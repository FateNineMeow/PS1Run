# 10 评估：是否需要后台常驻

> 评估对象：需求 3.2「程序是否需要后台常驻，若可行尽量不常驻」。
> 评估基准：2026-11-24 的设计方案（运行方式三态 + 执行器/编辑器探测 + 文件关联）。
> 状态横幅：结论已落地为代码——无窗口直通、`OnExplicitShutdown` 与"无参数才显示主界面"均已实现，8/8 组单测通过；§4.3 中的注册表写入互斥量仍为**设计未落地项**（见 [04 D18](04-progress.md#3-差距清单需求-vs-现状)）。本页结论未因实现而改变。

---

## 1. 结论

**不需要常驻。**

推荐形态：**按需启动 → 分发 → 立即退出**。进程生命周期以"毫秒到数百毫秒"计，不在后台保留任何服务、托盘图标或自启动项。

同时明确：**"选择"模式（Ask）只会多弹一个 460×300 的小窗，不构成常驻理由**（详见 §5）。

---

## 2. 依据

### 2.1 触发机制本身不需要常驻

文件关联是**注册表声明式配置**：Explorer 在用户双击时自己读取注册表并拉起命令。整个过程没有任何环节需要"提前运行一个进程等着"。

```
注册表（静态）  →  Explorer 读取  →  拉起 Ps1Run.exe  →  分发  →  退出
```

对比真正需要常驻的场景（本项目都不具备）：

| 需要常驻的典型特征 | 本项目是否具备 |
|---|---|
| 需要监听文件系统变化（FileSystemWatcher） | ❌ 否 |
| 需要接收来自其他进程的消息（IPC / 命名管道 / 窗口消息） | ❌ 否 |
| 需要定时任务（Timer / 计划） | ❌ 否 |
| 需要维持长连接（网络 / 设备） | ❌ 否 |
| 需要托盘图标持续交互 | ❌ 否（需求未要求托盘） |
| 需要预热缓存以降低首次响应延迟 | 🟡 理论上有一点，但收益极小（见 §2.3） |

### 2.2 常驻的代价是确定的

| 代价 | 量化/说明 |
|---|---|
| 内存占用 | 一个 WPF 进程常驻约 50–120 MB（工作集） |
| 开机自启污染 | 需写 `Run` 键或启动项，用户会感知、会反感 |
| 单实例与 IPC 复杂度 | 常驻就必须处理"第二实例把参数转交给第一实例"，需命名管道/窗口消息，代码量与故障面显著增加 |
| 崩溃恢复 | 常驻进程崩溃后，用户双击会"没反应"，体验反而更差 |
| 安全软件关注度 | 常驻 + 写注册表 + 拉起进程的组合更容易被启发式规则标记 |
| 升级/卸载 | 需处理"文件被占用无法替换"，卸载时要先杀进程 |

### 2.3 唯一收益不足以支撑常驻

常驻唯一能带来的是"冷启动更快"。估算：

| 形态 | 冷启动到目标程序被拉起 | 用户感知 |
|---|---|---|
| net48 按需启动 | 约 80–200 ms（含 JIT） | 双击后几乎立刻有反应 |
| net11 按需启动 | 约 120–300 ms | 同上 |
| 常驻 | 省掉进程启动，约 10–30 ms | **差异不可感知** |

而人类的点击反馈阈值约 100 ms 以上才明显。节省 100 ms 却要付出上百 MB 内存和一套 IPC 机制，性价比极低。

---

## 3. 成本对比

| 维度 | 按需启动（推荐） | 常驻 |
|---|---|---|
| 内存 | 分发期间短暂占用，退出即释放 | 50–120 MB 持续占用 |
| 自启动项 | 无 | 需要 |
| 代码复杂度 | 低（无 IPC、无单实例转发） | 高（单实例 + 参数转发 + 生命周期管理） |
| 故障影响面 | 单次分发失败，可重试 | 进程挂了则所有双击失效 |
| 卸载难度 | 低（无占用） | 需先终止进程 |
| 冷启动 | 80–300 ms | 10–30 ms |
| 安全软件风险 | 低 | 中 |

## 4. 落地手段

不常驻，但体验不打折。以下五项手段配合使用。

### 4.1 无窗口直通模式（核心）

带参数启动时**不创建主窗口**，执行完分发立刻退出。以下是简化示意；正式实现见 `Ps1Run.App\App.xaml.cs`（还包含最早调用 `CoreBootstrap.Initialize()`、`DiagnosticsLog.BeginSession/EndSession` 与全局异常兜底）：

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    var opts = CommandLineOptions.Parse(e.Args);

    if (opts.HasScript)          // --open / --run / --edit / --ask / 裸路径
    {
        ShutdownMode = ShutdownMode.OnExplicitShutdown;
        var code = _dispatcher.Run(opts);   // 内部同步完成分发
        Shutdown(code);
        return;
    }

    // 无文件参数才显示主界面
    ShutdownMode = ShutdownMode.OnMainWindowClose;
    new MainWindow().Show();
}
```

**效果**：`Run` / `Edit` 两种运行方式下，用户双击脚本 → 短暂停顿 → 目标程序出现，**中间不闪任何窗口**。

### 4.2 `ShutdownMode` 的选择

| 值 | 问题 |
|---|---|
| `OnLastWindowClose`（默认） | `Ask` 弹窗关闭后若没有其他窗口，进程会退出——看似正确，但若之后还要写日志/更新设置就可能被中断 |
| `OnExplicitShutdown`（推荐） | 由代码显式 `Shutdown(code)`，退出码可控、清理顺序确定 |

**当前实现**：带脚本参数（直通 / Ask）时用 `OnExplicitShutdown`，在分发结束时显式 `Shutdown(code)`，退出码可控；无参数主界面用 `OnMainWindowClose`（`App.xaml` 默认是 `OnLastWindowClose`，启动时覆盖）。

### 4.3 不做强制单实例

| 方案 | 结论 |
|---|---|
| 强制单实例 + 参数转发给已有实例 | ❌ 不需要。直通模式无共享状态，多开无害，省掉一整套 IPC |
| 完全允许多开 | ✅ 采用。用户连点两次 `.ps1` 就起两个独立进程，各自分发，互不干扰 |
| 注册表写入段加命名互斥量 | **设计未落地**（见 [04 D18](04-progress.md#3-差距清单需求-vs-现状)）：`Global\Ps1Run.Association` 尚未用于保护注册/注销临界区，与常驻结论无关 |

### 4.4 不做外壳扩展

有观点认为"右键菜单要用 shell extension"。本项目**不需要**：`shell\<verb>\command` 是注册表声明式的右键菜单，由 Explorer 直接解析，无需写任何 DLL。而 shell extension 是 Explorer **进程内加载**的组件，也不是常驻 exe，与本评估无关。

### 4.5 不做开机自启

不写 `HKCU\...\Run`、不建启动快捷方式、不注册计划任务。这样卸载干净、不打扰用户，也降低安全软件关注度。

## 5. "选择"模式对结论的影响

新增的 `Ask` 运行方式会在每次双击时创建一个 `PickerWindow`。需要确认它是否改变了"不常驻"的结论：

| 质疑 | 回答 |
|---|---|
| 弹窗是否意味着程序要一直活着？ | 否。窗口关闭（无论选中还是取消）后进程立即 `Shutdown`，生命周期仍以秒计。 |
| 是否为了"弹窗更快"而需要预热常驻？ | 否。窗口创建约 20–60 ms，用户本来就预期"要选一下"，这点延迟完全可接受。 |
| 弹窗失败时会不会需要后台守护？ | 不会。失败按 [05 §6.4](05-architecture-flows.md#64-无法交互的极端情况) 直接以退出码 4 结束，不做任何后台补偿。 |
| 是否需要常驻以便"记住上次选择"？ | 不需要。偏好写在 `config.cfg` 里，下次启动时读取，与进程是否常驻无关。 |

**结论：`Ask` 模式只增加一次短生命周期的窗口创建，不改变"不常驻"的结论。**

---

## 6. 进程生命周期（最终形态）

```
双击 .ps1
   │
   ├─ [RunMode = Run]  → 解析 PS → Process.Start → Exit(0)        总耗时 < 1s
   ├─ [RunMode = Edit] → 解析编辑器 → Process.Start → Exit(0)      总耗时 < 1s
   └─ [RunMode = Ask]  → 显示 PickerWindow
                          ├─ 选执行 → 同上 → Exit(0)
                          ├─ 选编辑 → 同上 → Exit(0)
                          ├─ 取消   → Exit(0)
                          └─ 异常   → Exit(4)
```

任何分支都不存在"分发后继续运行"的路径。

## 7. 何时需要重新评估

若未来出现以下需求，本结论需要复核：

| 触发条件 | 届时方案 |
|---|---|
| 要求"全局快捷键唤起" | 需要常驻或注册 `RegisterHotKey`（注册表/系统级绑定） |
| 要求"监控某目录下脚本自动执行" | 需要常驻 + `FileSystemWatcher`，或改用计划任务 |
| 要求"托盘常驻管理后台队列" | 需要常驻，且要重新评估 IPC 与单实例 |
| 要求"毫秒级批量连续调用"（如脚本被其他程序高频调用） | 可考虑常驻 + 命名管道，但要先证明按需启动的延迟确实是瓶颈 |

---

## 8. 评估小结

| 问题 | 结论 |
|---|---|
| 需要后台常驻吗？ | **不需要** |
| 能满足"尽量不常驻"的要求吗？ | **完全满足**，且是设计前提 |
| 不常驻会不会影响体验？ | 不会。无窗口直通模式消除闪烁，冷启动差异不可感知 |
| 唯一的例外场景？ | 仅在出现全局快捷键/目录监控/托盘队列等新需求时才需重新评估 |
